# RevenueCat Integration — Design

**Date:** 2026-07-12
**Status:** Approved (brainstorm complete)
**Scope tier:** Full suite

## 1. Goal

Connect RevenueCat (RC) to MyAmpix so subscription lifecycle data flows into the analytics
product: webhook ingestion, user-identity linking from the mobile SDK, subscription events in
the user timeline, a dedicated Subscriptions page, and subscription-based filtering across
every analytics surface — answering *why, from where, and when* users subscribed.

## 2. Hard constraints

1. **Strictly optional.** A project that never connects RC behaves byte-for-byte as today:
   no nav entries, no filter chips, no profile cards, no KPI changes, no schema-driven
   behavior differences. The existing Revenue page (SDK `$in_app_purchase`) is untouched
   in both modes.
2. **No scheduler exists** in the backend — no cron/background-job runner may be assumed.
   All sync work is request-triggered or fire-and-forget async from a request.
3. Webhooks must never lose data: journal first, process after, replay on failure.
4. RC API key is write-only from the dashboard (returned masked after save). Never logged.

## 3. Locked decisions (from brainstorm)

| Decision | Choice |
|---|---|
| Identity link | **Both**: convention (webhook `app_user_id` matches a known distinct_id/alias) + explicit SDK override `setRevenueCatAppUserId()` |
| Storage | **Events + state table**: `$rc_*` ClickHouse events for timeline/funnels/insights + Postgres `SubscriptionState` for current-status truth |
| RC REST API | **Webhook + API backfill** (RC API v2) for pre-existing subscribers and on-demand reconciliation |
| UI layout | **Revenue page + separate Subscriptions page** (Subscriptions only visible when connected) |
| Filtering | **Both**: `$rc_*` profile properties as the engine (zero query-engine changes) + a polished "Subscription" quick-chip UI on top |
| Scope | **Full suite** (core + standard + deep extras, see §8) |

## 4. Backend — new bounded context `backend/src/revenuecat/`

Nothing outside this module changes behavior when no integration row exists.

### 4.1 Prisma models

- **`RevenueCatIntegration`** — one per project. Fields: `projectId` (unique FK),
  `webhookSecret` (generated by us), `apiKey` + `rcProjectId` (RC API v2; masked on read),
  `sandboxMode` (bool: process or drop `environment: SANDBOX` events), `lastWebhookAt`,
  processed/failed/unlinked counters, `connectedAt`. **Row exists ⇔ RC connected** — this is
  the single gating fact for every feature in this spec.
- **`SubscriptionState`** — current truth per `(projectId, rcAppUserId)`. Fields: linked
  `distinctId` (nullable until identity resolves), `status`
  (`trial | active | grace | paused | churned | expired`), `productId`, `store`,
  `periodType`, `firstPurchaseAt`, `expiresAt`, `cancelledAt`, `totalSpentCents` +
  `currency`, `managementUrl`, `lastEventAt`. Powers profile cards, page KPIs, and fast
  "is subscriber?" answers without scanning event history.
- **`RevenueCatWebhookEvent`** — journal of every received webhook. Fields: RC event `id`
  (unique → idempotency), raw payload (jsonb), `status` (`processed | failed | unlinked`),
  `error`, timestamps. Doubles as the dead-letter queue for the health monitor + replay.

### 4.2 Webhook endpoint

`POST /webhooks/revenuecat/:projectId` — public route (RC is the caller, no JWT). Guard:
constant-time compare of the `Authorization` header against the project's `webhookSecret`.
The user pastes our generated URL + header value into the RC dashboard.

Per-event flow (respond 200 fast; heavy work must not block RC's retry policy):

1. Authenticate (401 on mismatch; no integration row → 404).
2. Dedup on RC event id (already journaled → 200 no-op).
3. Journal raw payload.
4. Drop or process per `sandboxMode` when `environment == SANDBOX`.
5. Normalize event type → ClickHouse event name (see §4.3).
6. Resolve identity (see §4.4).
7. Write ClickHouse event on the resolved distinct_id with properties: price, currency,
   product id, store, period type, entitlements, environment, cancellation reason (when present).
8. Upsert `SubscriptionState`.
9. Write `$rc_*` profile properties via the existing profile-writer (§4.5).
10. Mark journal row `processed` (or `failed` with error; `unlinked` if identity unresolved).

### 4.3 Event type mapping

| RC webhook type | ClickHouse event |
|---|---|
| `INITIAL_PURCHASE` | `$rc_initial_purchase` |
| `RENEWAL` | `$rc_renewal` |
| `CANCELLATION` | `$rc_cancellation` |
| `UNCANCELLATION` | `$rc_uncancellation` |
| `NON_RENEWING_PURCHASE` | `$rc_non_renewing_purchase` |
| `EXPIRATION` | `$rc_expiration` |
| `BILLING_ISSUE` | `$rc_billing_issue` |
| `PRODUCT_CHANGE` | `$rc_product_change` |
| `SUBSCRIPTION_PAUSED` | `$rc_paused` |
| `TRANSFER` | `$rc_transfer` |
| `TEST` | journaled `processed`, no event written |
| unknown/future types | journaled `processed` with a note, no event written (forward-compatible) |

### 4.4 Identity resolution ("both" decision)

Order of resolution for a webhook `app_user_id`:

1. **Explicit link** — the SDK's `setRevenueCatAppUserId(id)` emits a `$rc_link` event; the
   backend records `rc_app_user_id ↔ distinct_id` in the identity/alias system.
2. **Convention** — `app_user_id` matches a known distinct_id or alias directly
   (covers apps that call `Purchases.logIn()` with the MyAmpix distinct_id).
3. **Unlinked** — journal the event as `unlinked`. When a matching link later arrives
   (via `$rc_link` or a new alias), unlinked events for that `app_user_id` are
   **automatically replayed and attached**. Webhook-before-first-app-open ordering is safe.

`$RCAnonymousID:*` app_user_ids can only resolve via explicit link (path 1) and otherwise park
as unlinked.

### 4.5 Profile properties (the filter engine)

Written through the existing profile-writer:

`$rc_status`, `$rc_product_id`, `$rc_store`, `$rc_period_type`, `$rc_total_spent`,
`$rc_first_purchase_at`, `$rc_expires_at`, `$rc_cancelled_at`.

Users with no RC data simply lack the properties (no default writes).

**Amendment (plan-time finding):** the shared filter compiler only reaches
`events.properties`, not `user_profiles.properties`. Supporting profile-property filters
requires one **additive** query-engine extension (no change to existing filter behavior):

- `insightsFilterSchema` gains an optional `target: 'event' | 'profile'` (default `event`,
  so every existing saved filter/report is untouched).
- Filters with `target: 'profile'` compile to a `distinct_id IN (SELECT distinct_id FROM
  user_profiles FINAL WHERE …JSONExtract…)` predicate — the same shape as the existing
  cohort predicate (`applyCohortPredicate`).
- Cohorts gain a new additive condition type `{ type: 'profile', property, op, value }`
  compiled against `user_profiles FINAL`; existing `behavior`/`did_not`/`property`
  conditions are unchanged. Auto-created cohorts use it.

### 4.6 Backfill & reconciliation (no cron)

- **On connect** (when API key + rcProjectId provided): fire-and-forget async job pages RC
  API v2 (`/projects/{id}/customers` → subscriptions/entitlements) and seeds
  `SubscriptionState` + profile properties for pre-existing subscribers.
  **State only — no synthetic ClickHouse events** (no fake timeline history).
- **On demand**: per-user "Refresh from RevenueCat" (profile card) and project-level
  "Re-sync" (settings) hit the same sync code path.
- Backfill progress/status surfaced on the settings health panel.

### 4.7 Management API (dashboard-facing, project-scoped)

Guarded per the per-project-roles model — reads = viewer, config mutations = admin:

- `GET /projects/:id/integrations/revenuecat` — status, health counters, masked key.
- `PUT /projects/:id/integrations/revenuecat` — connect/update (generates webhookSecret on create).
- `DELETE …` — disconnect: removes config + gating flag, **keeps** historical events/state.
- `POST …/resync` — project-level re-sync; `POST …/replay` — replay failed/unlinked journal rows.
- `GET …/events` — journal page for the health panel.
- Per-user refresh endpoint for the profile card.

The projects payload (or a lightweight status endpoint) exposes `integrations.revenuecat: boolean`
for frontend gating.

## 5. Flutter SDK

- `Myampix.setRevenueCatAppUserId(String id)` — persists locally, emits `$rc_link`
  (re-emitted after identity changes such as `identify()`); cleared on `reset()`.
- Documented convention recipe (no SDK change needed):
  `Purchases.logIn(await Myampix.getDistinctId())`.
- **No RevenueCat dependency is added to the SDK** — integration stays optional there too.

## 6. Dashboard

### 6.1 Gating

`integrations.revenuecat` is read once into project context (e.g. `useRcConnected()`).
Every surface below renders **only** when true. Frontend tests assert nothing RC-related
renders when disconnected.

### 6.2 Project settings → Integrations

RevenueCat connect card: generated webhook URL + Authorization secret (copy buttons),
API key + RC project id fields, sandbox toggle, "Send test" verification (RC `TEST` event
round-trip), and once connected a **health panel**: last webhook received, processed /
failed / unlinked counts, failed-event list with one-click replay, re-sync, backfill status,
disconnect.

### 6.3 Subscriptions page (new nav entry when connected)

- KPI row: MRR, active subscribers, in trial, new this period, churned, trial→paid rate.
- Subscriber trend + MRR movement over the global date range (uses global filters).
- Plan breakdown, store breakdown, churn-reason donut (voluntary vs billing issue vs expiration).
- Recent subscription events table; subscriber CSV export.
- **Attribution sections**:
  - *Conversion drivers* — top screens/events in the days before first purchase +
    first-session screen breakdown ("from where / why").
  - *Time-to-convert* histogram — first seen → first purchase ("when").
  - *Trial funnel* — trial start → conversion → retained (prebuilt).

### 6.4 User profile modal

- Subscription card: status badge, plan, store, renews/expires, total spent, first purchased,
  deep link to the customer in the RC dashboard (`managementUrl`/customer URL), per-user refresh.
- Timeline: `$rc_*` events styled distinctly + a "★ first subscribed" divider so
  before/after-subscription behavior reads at a glance.

### 6.5 Filters everywhere

- "Subscription" quick-chip in the global filter bar (status: active / trial / churned / …)
  that writes `$rc_status` property filters underneath — sugar over the untouched engine.
- `$rc_*` properties grouped under "Subscription" in every property dropdown.
- **Auto-created cohorts** on connect: Active subscribers, In trial, Churned, Billing issue.

### 6.6 Elsewhere

- Home: MRR + active-subscribers KPI tiles when connected.
- Live view: `$rc_*` events appear (they are normal events) with subscription styling.
- Revenue page: unchanged; may show a link to Subscriptions when connected.

## 7. Error handling

- Webhook auth failure → 401, no journal. Unknown project / no integration → 404.
- Processing failure after journal → journal `failed` + error; replayable; endpoint still 200s
  where the payload was accepted (RC retries only on non-2xx; we prefer our own replay).
- ClickHouse/profile write failures → `failed` journal status, health panel surfaces count.
- Backfill API errors → recorded on integration status; partial progress kept; re-runnable.

## 8. Feature checklist (full suite)

**Core:** connect card, webhook (auth, idempotent, journaled), identity (convention +
explicit link + unlinked replay), `$rc_*` events + `SubscriptionState`, profile properties,
API backfill, timeline styling + first-subscribed divider, profile subscription card,
Subscriptions page core KPIs/breakdowns, filter chip + property groups.

**Standard extras:** auto-cohorts, conversion drivers, time-to-convert, trial funnel,
Live view styling, Home KPI tiles, subscriber CSV export.

**Deep extras:** churn-reason breakdown (incl. billing issues/grace), webhook health monitor +
failed-event replay, per-user RC dashboard deep link, sandbox toggle, per-user +
project-level re-sync.

**Explicitly out of scope:** alerts on subscription events (needs the missing scheduler),
LTV-by-acquisition modeling beyond the conversion-drivers report, RC promotional-offers
management, server-side receipt validation (RC's job).

## 9. Testing (TDD, London school)

- Webhook processor: one spec per event type; idempotency (duplicate event id);
  sandbox drop/process; unlinked → linked replay; unknown-type forward-compat.
- Auth guard: constant-time compare, 401/404 paths.
- Identity resolution order: explicit link > convention > unlinked.
- Backfill: pagination, partial-failure resume, state-only writes (no events).
- Management API: role guards (viewer read / admin mutate), masked key.
- SDK: link event emission, persistence, reset clearing.
- Frontend: gating (disconnected → zero RC UI), settings card, Subscriptions page,
  timeline divider, filter chip → property-filter translation, auto-cohorts.
- All existing suites stay green untouched.

## 10. Phasing

1. **P1 Backend core** — models + migration, webhook endpoint, identity, event mapping,
   `SubscriptionState`, profile properties, journal.
2. **P2 SDK** — `setRevenueCatAppUserId` + `$rc_link` handling.
3. **P3 Settings UI + gating** — connect card, status flag, health panel.
4. **P4 Subscriptions surfaces** — page core, profile card, timeline styling.
5. **P5 Full suite** — filter chip + property groups, auto-cohorts, attribution sections,
   Home/Live touches, backfill + re-sync + replay tooling.

Each phase lands with its tests; the gating constraint (§2.1) holds at every phase boundary.
